## Two-plane decision (explicit)
The merge is a single-plane ETL transform. I did **not** promote its stages (readdir/parse → seed nodes → union fields → dedupe flows/hotspots/terms → validate → build meta → write) to aggregates/policies/events. The whole pipeline lives in `cmd-merge-traces.tactical.explanation`. Only two domain-significant facts are promoted to events: `evt-model-merged` (the union + derived meta) and `evt-model-validated` (zero-error validation). The validation rules are **invariants on `agg-model`**, attached via `enforces` edges, not policies and not in `steps`. Forcing command/aggregate grammar onto parse/seed/validate would have been over-modeling.

## Surprises / contradictions (the payoff)
1. **The two callers disagree on invalid models** → hotspot `hot-invalid-model-written`. `merge-flows.js` writes `outFile` (line 31) *before* it inspects `errors` (line 37), then exits 1 — so a failed validation still leaves an invalid `flows.json` on disk. `mergeTraceDocs` never returns `null` on validation errors (it always builds the model object; `null` only comes from `mergeTracesDir` when the dir is empty). The server's `resolve-model.mjs` does the opposite: it **throws** on `merged.errors.length` and serves nothing. So the same invalid trace set yields a persisted-but-flagged file via the CLI and a hard failure via the server. That inconsistency is the human question worth surfacing.
2. **Validation errors do not stop model assembly.** Errors are accumulated into an array and the full model is still built and returned. Validation is advisory to the *caller*, not a gate inside the library. Clean separation, but it's why (1) is possible.
3. **`fields[]` union authority is order-dependent.** Re-seen nodes union `fields` by name with "the data pass is authority" (line 97, later file overwrites). Since `mergeTracesDir` sorts files alphabetically (line 239), a data-mapping trace only wins if its filename sorts *after* the behavioral trace that first defined the node. That's an implicit ordering contract not documented in the schema — worth a heads-up for the data-mapping phase (name its files to sort last, or don't rely on order).
4. **`inferred: false` is sticky and one-way** (line 91): once any trace declares a node code-named, no later trace can flip it back to inferred. Fine, but means the *first* agent to assert `inferred:false` wins permanently.

## Modeling choices worth flagging
- `rm-trace` (the per-flow trace JSON) modeled as a **read model** the command `reads`, with `projects from ext-source-fs` to show its filesystem origin, per the briefing's steer. It's the input artifact, not an aggregate.
- `agg-model` `persists to ext-source-fs` represents the CLI's `writeFileSync`. I used `persists to` (a valid edge verb) even though the target is an externalSystem, not a `table` — see friction below. The server path holds `agg-model` purely in memory; noted in tactical.
- `ext-source-fs` is `inferred: false` (the code literally uses `node:fs`); all behavioral nodes are `inferred: true` (recovered ES concepts). Followed the schema's inversion.
- No `fields[]` / storage lineage built here — deferred to the data-mapping phase per the briefing. `agg-model`'s store is a file (`flows.json`) or in-memory `state`; noted in tactical, not modeled as columns.

## Schema friction (PILOT — candid)
- **The data-model edge verbs assume a SQL target and don't fit a file-based/ETL codebase.** `persists to` / `projects from` / `writes` / `connects via` are all typed in the schema as pointing at `table`/`server` physical nodes. But this system's "store" is the **filesystem** (an `externalSystem`) and an **in-memory `state` object** — there is no `table`. I reused `persists to` for `agg-model → ext-source-fs` and `projects from` for `rm-trace → ext-source-fs`, which reads slightly off (the target isn't a table). The merge doesn't validate edge targets by type so it passes, but the *vocabulary* has no clean verb for "materializes to a JSON file" or "reads from the filesystem." Consider either (a) blessing `ext-*` filesystem/in-memory stores as legitimate targets for these verbs, or (b) telling agents to fall back to plain `reads`/`writes`/`updates` for file/in-memory stores and keep `persists to`/`projects from` for real databases. Right now it's ambiguous and every agent will improvise differently.
- **No first-class way to say "this aggregate's state is an in-memory object vs a file vs external."** `ownedBy` covers "state lives in an external system," but the merge/state/model aggregates here are backed by a process-local JS object or a JSON file, which is neither `ownedBy` nor a physical `db/table`. The briefing patched this by saying "note the store in tactical," which works, but it means the store distinction is invisible in the graph. A lightweight `store` hint (`file | memory | external | db`) on aggregates would capture what this codebase is actually about.
- **"Command lookups use `reads`" vs the read side of an ETL command is awkward.** The schema frames `reads` as "gating data / join keys" — an *incidental* lookup. But for the merge, reading the trace files IS the command's whole input, not a side lookup. Modeling the primary input as `cmd reads rm` felt like underselling it; there's no verb for "consumes as primary input." Not blocking, but the briefing could say explicitly: for ETL/read-heavy commands, model the primary input as a read model the command `reads`.
- **Invariant clustering guidance is good but the "how many" line is fuzzy.** The schema says invariants attach 1:1 to aggregates via `enforces`; the briefing says cluster. Those pull in opposite directions and I had to use judgment (4 clusters over ~18 raw error checks). Fleet agents will vary in granularity here unless the briefing gives a firmer rule (e.g. "one invariant per *contract*, cite line ranges" — which is what I did). Recommend making that explicit for consistency across the fleet.
- **`status` default is silent-ish.** A flow missing `status` warns and is coerced to `live` (line 154). That's fine, but combined with the CLI-writes-on-error behavior, warnings are easy to miss. Not a schema issue per se — just that "warning vs error" is the whole safety model and it's load-bearing.
- Everything else in the schema fit cleanly. The two-plane guidance in both the schema and briefing was the single most useful instruction for this codebase — without it I'd have over-modeled the pipeline stages.
